# PROJECT_STRUCTURE

이 문서는 저장소의 **실제 파일 배치**와, 포트폴리오/게임 프로젝트 관점의 **논리적 역할 분리**를 함께 설명합니다.

## 정리 원칙

1. **실행 안정성 우선**: import 경로, 빌드/배포 동작을 깨뜨릴 가능성이 있으면 물리적 이동을 하지 않습니다.
2. **논리 구조 명확화**: README와 본 문서에서 런타임/콘텐츠/데이터/검증/운영 문서의 책임을 분리해 설명합니다.
3. **역할 중복 최소화**:
   - 로드맵/기획 상세: `ROADMAP.md`
   - 운영/배포/키/복구: `OPERATIONS.md`
   - 본 문서: 파일 구조와 디렉터리 책임 정의

## 현재 구조를 게임 프로젝트 관점으로 해석

| 역할 | 실제 경로 | 책임 |
| --- | --- | --- |
| 게임 런타임 및 화면 | `app/` | 화면 렌더링, 휴대폰 UI, 스토리 진행, API 엔드포인트 |
| 시나리오/대사/사건 데이터 | `content/` | 사건 원본(`cases`), 스키마(`schema`), 생성물(`generated`), 보관(`archive`) |
| 저장 데이터 계층 | `db/`, `drizzle/` | 스키마 정의 및 마이그레이션 메타데이터 |
| 정적 리소스 | `public/` | 픽셀 아트/OG 이미지/파비콘 |
| 콘텐츠 빌드/검증 | `scripts/` | 콘텐츠 통합, 대화·출시 검사, 스토리/UI 테스트 스크립트 |
| 루트 설정 파일 | `package.json`, `tsconfig.json`, `vite.config.ts` 등 | 런타임/빌드/품질 기준 |
| 프로젝트 문서 | 루트 `*.md`, `docs/` | 로드맵/운영/보안/권리/출품 컨텍스트 |

## 왜 이번에는 파일 이동을 하지 않았나

- `app/story/*`, `app/game-data.ts`, `scripts/*`는 경로 결합도가 높고,
  콘텐츠 생성물(`content/generated/cases.json`)을 직접 참조합니다.
- 물리적 이동은 import 경로/검증 스크립트/배포 설정에 연쇄 수정을 유발할 수 있어,
  이번 작업 목표(포트폴리오 가독성 개선) 대비 리스크가 큽니다.
- 따라서 **실제 파일은 유지**하고, 문서에서 역할을 명확히 드러내는 방식으로 정리했습니다.
