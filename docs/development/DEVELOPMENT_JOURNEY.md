# 사기방지위원회 — 개발 시행착오

목적: AI를 통해 단순 사기 사례 재현보다 고정적이고 반복적인 대화를 줄이고 실제 사기 상황에 처한 것과 같은 체험을 하는 것이 목적이다.

이 문서는 **LLM 게임 프로젝트의 개발 대화에서 제기된 문제를 현재 코드·커밋·검사와 대조한 기록**입니다. 요청을 받았다는 사실과 해결이 구현됐다는 사실을 구분하며, 대화 원문 대신 재현 상황과 판단 근거를 요약합니다.

- 현재 실행 기준: [공개 데모 v76](../game/PUBLIC_DEMO.md#확인-기준). 과거 사건 수·모델 실험·호출 제한은 개발 과정으로만 설명합니다.
- 확인 근거: 대화의 재현 보고 → 원인을 바꾼 커밋 → 현재 구현 → 해당 회귀 검사 순으로 연결합니다.
- 과거 소수의 실응답 관찰을 현재 성공률·속도·사용자 만족도로 일반화하지 않습니다. 이번 문서 보강에서는 브라우저·실기기·실제 Gemini 호출을 추가하지 않았습니다.

## 문제와 목표

- 반복되는 고정 대사를 줄이되, 인물이 알 수 없는 사실이나 하지 않은 행동을 AI가 만들어 내지 않게 하기.
- 친숙한 이름, 화면 속 수치, 손실을 되찾고 싶은 마음이 선택에 미치는 영향을 체험하게 하기.
- 송금한 경로뿐 아니라 확인·보류·차단한 경로도 다음 사건으로 자연스럽게 이어지게 하기.
- AI가 실패해도 완주할 수 있고, 생성된 문장이 거래·잔액·결말을 직접 바꾸지 않게 하기.

## AI의 현실감과 응답 안정성

### 표현은 유연하게, 게임 결과는 코드로

개발 대화에서는 고정 예시를 반복하는 답변, 질문보다 감정 표현을 앞세우는 답변, 첨부를 무시하는 단답이 문제로 제기됐습니다. 반대로 답변의 키워드를 너무 엄격하게 검사하면 맥락에 맞는 문장도 탈락했습니다.

| 문제 | 원인 | 해결 | 결과 |
| --- | --- | --- | --- |
| 같은 반응 분류이면 대사도 비슷해짐 | 예시·표현 규칙에 생성 문장을 과도하게 맞춤 | `reply`는 현재 메시지·첨부·진행 문맥으로 새로 생성 | 말투의 다양성과 진행 분류를 분리. 자연스러움 전체가 보증된 것은 아님 |
| 송금 전후·사건 종료 여부를 답변이 반영하지 못함 | 메시지만 보내고 확정된 진행 맥락을 충분히 전달하지 않음 | 허용 상태 ID와 관계를 검사한 뒤 서버에서 프롬프트 문장으로 변환 | `storyContextFor / validateStoryContext / storyContextText`로 임의 문맥·모순된 조합 제한 |
| 표현을 완화하면 잘못된 분기도 허용될 위험 | 자연어의 유연성과 게임 상태 검증을 한 규칙으로 취급 | `reaction / supportMode / focus`와 첨부 일치 조건은 엄격히 유지 | 답변이 송금·신고·환급을 실행하지 않음. 허위 완료와 실제 연락처 등도 제한 |

## 메시지 순서 오류를 해결한 과정

대표 재현은 **2막에서 AI 답장을 받은 뒤 송금하고 준비된 후속 메시지를 보내는 경로**였습니다. 새 사용자 메시지가 이전 AI 답변 앞에 끼어들어, 스크롤을 아래로 옮겨도 대화 순서 자체가 틀렸습니다.

```text
기대 순서: 사용자 첫 메시지 → AI 첫 답변 → 송금 후 메시지 → 후속 답변
오류 순서: 사용자 첫 메시지 → 송금 후 메시지 → AI 첫 답변
```

| 접근·문제 | 원인 | 해결 | 결과 |
| --- | --- | --- | --- |
| 하단 이동·대화 연속성 보완 뒤에도 순서 오류 재발 | 보이는 위치와 DOM의 메시지 배치 순서는 별개. `sent / preparedSent / reply` 고정 슬롯은 발생 순서를 보존하지 못함 | 개인 대화를 ID가 있는 단일 `transcript` 배열로 관리하고 전송·응답을 끝에 추가 | 후속 메시지 여러 쌍의 순서·첨부·ID 고유성 검사 |
| 단계가 바뀌면 본편 AI 답장이 새 대화 뒤로 밀림 | 결정 답장을 항상 대화 끝에 렌더링 | 발생한 `stage / after` 위치에 고정해 작성 대사 사이에 배치 | 송금 전 답변이 송금 후 메시지보다 앞에 유지되는 SSR 검사 |
| 예전 메모리 형식이나 다른 인물·모드와 충돌할 위험 | 새 배열이 없는 데이터와 대화 단위의 상태가 공존 | 기존 슬롯을 초기 배열로 변환하고 본편·체험·연습·사건·인물별 메모리 분리 | 구형 데이터 변환, 준호/지수 및 모드 격리 검사 |

## 검증과 저장소 운영에서의 시행착오

### 재현 상황을 회귀 검사로 남긴 이유

대사·첨부·화면·서버를 따로 수정하면 한쪽의 개선이 다른 쪽의 허용 조건과 충돌했습니다. 따라서 문제가 재현된 **선택 순서와 데이터 조합**을 검사로 남겼습니다.

| 검사 | 방지하려는 문제 | 검증의 경계 |
| --- | --- | --- |
| `content:check` | 원본·생성물 불일치, 필드·단계·안전 검수표 누락 | 콘텐츠 근거 전체의 사실 검증은 별도 |
| `dialogue:check` | 내장 대사의 위험 표현·길이·반복 | 실제 Gemini 품질 평가와 별개 |
| 진행·첨부 검사 | 중복 거래, 저장 재생, 사건·모드 오염, 첨부 조건 불일치 | 실제 터치 흐름은 별도 |
| 메시지 순서·UI 검사 | AI 이후 후속 메시지 순서, 구형 메모리, 렌더링·읽음 회귀 | SSR·소스 검사는 픽셀 배치 검수가 아님 |
| 모의 API·공용 예산 검사 | 응답 수정 횟수, 지연·할당량 분류, 서버 방어·공유 예약 | 실서비스 가용성·과금 상한을 보장하지 않음 |
| 보고서 검사 | 의도를 실제 행동으로 오인, 미진행 사건 포함, 복원 후 결과 차이 | 개인의 취약성 진단이 아님 |
| `docs:check`, lint·타입·빌드 | 깨진 문서·파일명·참조, 정적 오류·배포 산출 실패 | 공개 사이트 재배포와 별개 |

현재 남은 과제:

- 자료 구매·추가 비용으로 서사를 바꾼 뒤에도 `one-shot.js`의 진행 문맥 등에 남은 투자 참여·출금 표현이 화면·메모와 일치하는지 정합성 점검. 이번 문서 보강에서 실행 코드는 수정하지 않았습니다.
- 실제 배포 저장의 v3/v4 호환과 모바일 키보드·주소창·뒤로가기·긴 대화를 대상 버전별로 계속 확인하고, 기존 [UI 검수 기록](UI_REVIEW.md)에 조건을 보완하기.
- 내장 대사 전환을 포함한 현재 버전의 응답 품질·지연과 플레이 분량·설명 이해도를 관찰 조건과 함께 기록하기. 개선 성과와 사용자 반응은 확인 필요.
- 실제 시연·출품 대상의 음원·이미지·외부 서비스 이용 조건과 권리 증빙 확인.
- 이후 배포마다 소스 SHA·검증·저장 호환·배포 상태를 함께 갱신하기. 실응답 평가는 명시적 허용이 있는 경우 기본 CI와 분리해 실행하기.

우선순위와 완료 조건은 [ROADMAP](ROADMAP.md)에서 관리합니다. 대화에서 제안된 계획이나 과거의 제한된 관찰을 현재 구현·검수 완료로 바꾸어 적지 않습니다.
